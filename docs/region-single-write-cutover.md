# W7 행정구역 단독 쓰기 전환 준비

이 문서는 [W7 작업](https://github.com/toilet-project/toilet-api/issues/128)의 1단계 운영 판단 자료다. API의 관리자 확정은 `toilet_region_decision`에만 기록하고, 배치 판정은 `toilet_region_assessment_history`와 `toilet_region_assignment`에만 기록한다. 배치의 재시작·재검토 조회도 assignment가 가리키는 history를 사용한다. 기존 `toilet_region`과 `toilet_region_override`는 1단계 후에도 7일간 보존한다. Flyway V8/V16/V18은 적용 이력의 체크섬을 유지하기 위해 수정하지 않는다.

## 조기 1단계 전환 기준과 순서

운영 요청에 따라 14일간의 이중 기록 관찰을 배포 전 필수 조건에서 제외하고, 2026-09-22까지의 8회 연속 정기 배치와 신규·기존 기록 일치 결과를 배포 전 근거로 사용한다. 나머지 위험은 **단독 쓰기 배포 후 최소 7일간** 관찰한다. 이 변경은 14일의 이중 기록 근거를 모두 얻기 전에 전환한다는 위험을 명시적으로 받아들이는 일정 변경이다.

1. 배포 직전 읽기 전용 관찰을 다시 실행해 배치 성공·오류, 자동 판정과 관리자 결정의 legacy/new 불일치, 참조·revision 오염, API health를 확인한다. 기존 표본에서 새 조회가 약 16% 느렸으므로 성능은 여러 표본과 실제 응답에서 계속 확인한다. 불일치·오류·회귀가 발견되면 전환을 중단한다.
2. 이 변경의 두 CI 통과 커밋과 복귀 SQL을 고정한다. 현재 운영 API·배치 이미지 digest와 DB 백업 식별값을 기록하고, 다른 배포가 없음을 확인한다. 이 정보가 없으면 이미지를 교체하지 않는다.
3. 계정 상태를 보존하는 승인된 배포 경로로 API와 배치 이미지를 순차 교체한다. 교체 중 배치 동시 실행을 막는다. 새 API와 구 배치, 새 API와 새 배치의 조합은 모두 정규화 테이블에 기록한다.
4. 전환 직후 관리자 시·군·구 확정, 배치의 좌표 판정·재실행, 공개 지역 표시와 캐시 무효화를 확인한다. 기존 두 테이블에 새 기록이 생기지 않는지, 정규화 테이블과 서비스 응답이 일치하는지 매일 최소 7일간 관찰한다. 오류·데이터 불일치·실질적인 성능 악화가 생기면 아래 복귀 절차를 수행한다.
5. 2026-10-08 목표의 테이블 삭제는 최소 7일간 정상 결과, 제거 직전 백업, 별도 운영 승인 후에만 진행한다. 이 단계의 PR과 배포에 삭제 SQL을 포함하지 않는다. `toilet_region_assessment_history`는 계속 보존한다.

두 이미지가 모두 교체된 직후의 KST 시각을 `REGION_SINGLE_WRITE_CUTOVER_AT_KST` 저장소 변수에 `YYYY-MM-DD HH:MM:SS` 형식으로 기록한다. 일별 관찰은 이 시각 이후 기존 두 테이블의 새 기록과 정기 배치 실패가 0인지 확인하고, 신규 assignment·assessment·decision 기록량을 함께 보여준다. 교체 전에는 이 변수를 비워 둔다. 수동 관찰에서는 `cutover_at_kst` 입력으로 같은 기준을 지정할 수 있다. 기존 테이블의 전체 건수는 삭제 시점까지 보존되므로 전환 후 신규 테이블과 전체 건수를 매일 같게 유지할 필요는 없다.

## 1단계 복귀

이전 이미지는 이중 기록 코드가 있으므로 정규화 테이블을 그대로 사용할 수 있다. 다만 기존 배치의 체크포인트는 `toilet_region.result_json`을 읽는다. 복귀 전에 새 구조의 최신 판정과 관리자 결정을 기존 테이블에 채워야 불필요한 대량 재판정과 관리 데이터 누락을 피할 수 있다.

1. API 쓰기와 행정구역 배치를 중단하고 DB 백업·두 이미지 digest를 확인한다. 쓰기가 계속되는 동안 복귀 SQL을 실행하지 않는다.
2. [복귀 SQL](../src/main/resources/db/region-single-write/restore_legacy.sql)을 **오류 시 즉시 중단하는 동일한 DB 연결**에서 실행한다. 활성 revision의 assignment가 history·공식 코드와 연결되는지 먼저 검사하고, 기존 판정·확정 테이블을 트랜잭션으로 재구성한다. 검사 오류나 불일치가 있으면 같은 연결에서 `ROLLBACK`하고 이미지를 교체하지 않는다.
3. 결과의 `assignment_mismatch`와 `decision_mismatch`가 모두 0인지 확인한다. 기존 테이블과 현재 서비스 뷰의 대표 표본도 비교한다.
4. 고정해 둔 이전 배치·API 이미지를 계정 상태 보존 경로로 되돌린 뒤 API health, 관리자 확정, 공개 지역 조회, 다음 배치의 체크포인트와 캐시 이벤트를 점검한다. 정규화 테이블과 감사 이력은 삭제하지 않는다.

SQL은 활성 revision만 기존 테이블로 되돌린다. 과거 revision은 현재 서비스 값이 아니며 이전 배치가 필요하면 다시 평가한다. 복귀 SQL은 반복 실행할 수 있고, 격리 MySQL 시험에서 두 번 실행해 결과가 유지되는지 확인한다. 이미지 전환 전에 기존 테이블이 삭제되었다면 이 절차를 쓰지 않고 백업 복구 범위부터 별도로 판단해야 한다.
